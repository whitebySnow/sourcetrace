# 0005: 使用结构化声明渲染引用修复

状态：accepted
日期：2026-08-12

## 背景

真实 DeepSeek 评测中，检索通过且证据评估为充分的回答仍可能在初稿和一次修复后都返回
`uncited_claim`。引用诊断显示修复模型经常原样返回自由文本；有些草稿的全部结构单元都没有
引用，有些只遗漏开头或中间单元。仅在提示词中重复“每句带引用”不能稳定约束供应商输出。

## 决定

引用修复适配器不再要求供应商返回自由文本 `answer`，而是要求结构化 `claims` 数组。每个
claim 只包含 `text` 和 `citation_ids`：

- `text` 只能来自允许证据支持的声明内容，不包含模型生成的 UUID 引用；
- `citation_ids` 至少包含一个由适配器提供的允许 ID；
- 未知 ID、空声明、空引用和错误字段集合继续拒绝；
- 适配器按确定性单元切分规则，将每个 claim 的允许引用追加到其每个句子或列表项；
- 只有渲染后的文本再次通过工作流引用校验，才可成为最终回答。

初稿仍可通过现有 SSE 文本流展示；只有进入单次修复节点时使用结构化 claims。修复提示词版本
升级，历史 Answer Run 继续保留旧版本语义。

## 替代方案

1. 继续要求模型直接重写带引用的自由文本：已被真实评测中的原样修复和零引用修复否决。
2. 对标题或列表单元放宽校验：会允许事实性标题绕过证据门禁，违反严格引用不变量。
3. 由服务端按相似度自动猜测并补引用：无法证明声明与片段的支持关系，属于引用伪造。

## 后果

- 修复模型的输出契约更窄、更易测试，引用格式由代码负责而不是由模型负责。
- 修复节点可能改变原始 Markdown 布局，但不改变事实证据范围；不通过确定性校验仍然拒答。
- 供应商契约和评测报告必须记录新的修复提示词版本；真实评测仍需人工审核其最终回答。
